# Subpool Phase 1 测试用例

状态：Phase 1 测试基线

依据：Subpool 产品与技术设计（Phase 1 实现基线）

范围：Codex 订阅账号池、OpenAI 兼容数据面、管理控制面和 Docker Compose 自托管

## 1. 测试目标

本测试集用于证明 Phase 1 满足以下核心约束：

- 管理员凭据仅由环境变量提供，管理会话仅保存在进程内。
- Codex 订阅凭据可通过设备码安全导入、刷新、禁用和恢复。
- API Key 与账号池、上游账号的关系只能由服务端决定。
- 每个上游账号最多同时处理全局配置数量的请求，默认值为 3；API Key 数量不受该值限制。
- 新 Key 和允许迁移的新会话内置采用最少绑定优先，continuation 始终保持账号亲和。
- 正确代理 Responses、Chat Completions、Models 和 SSE 流式响应。
- 只按 API Key 和日期展示 input/output tokens，不保存聊天内容；内部只允许保存用于防重复计量的不可逆事件哈希。
- Docker Compose 可以在任意合法域名或内网地址下自托管，并支持升级、备份和恢复。

## 2. 测试层级与优先级

自动化层级：

- `UT`：单元测试，不依赖网络和 PostgreSQL。
- `IT`：集成测试，使用真实 PostgreSQL 和可控的 Codex Mock Server。
- `CT`：Provider 契约测试，验证 Subpool 与 Codex 上游协议的兼容性。
- `E2E`：从浏览器、Codex CLI 或 OpenAI SDK 经过完整服务链路执行。
- `DEPLOY`：基于生产镜像和 Docker Compose 的部署测试。
- `MANUAL`：仅用于无法稳定自动化的真实设备码授权、真实域名和发布验收场景。

优先级：

- `P0`：发布阻断，失败不得发布。
- `P1`：核心能力，发布前必须修复或有明确豁免。
- `P2`：增强覆盖，可在不影响核心闭环时延期。

## 3. 通用测试环境

- 使用生产构建方式生成的 Subpool 镜像和固定版本 PostgreSQL 镜像。
- Codex Mock Server 支持设备码授权、token refresh、Responses、SSE、401、429、usage 和连接中断脚本化响应。
- 测试账号均为虚构账号：`codex-a`、`codex-b`、`codex-c`、`codex-d`。
- 默认全局 `max_concurrent_requests_per_account=2`，对所有账号统一生效，除非用例另有说明。
- 测试 Key 均由被测服务临时生成，不把完整 Key 写入快照、测试日志或测试报告。
- E2E 测试结束后删除测试数据库和卷；备份恢复用例使用独立临时卷。
- 涉及时间的用例使用可注入时钟，避免真实等待冷却、过期或跨日。

## 4. 环境变量与启动配置

### TC-CFG-001 缺少管理员用户名时拒绝启动

- **前置条件**：已配置数据库和加密主密钥；未设置 `SUBPOOL_ADMIN_USERNAME`，已设置 `SUBPOOL_ADMIN_PASSWORD`。
- **步骤**：启动 Subpool 容器；读取退出码和启动日志。
- **期望结果**：服务启动失败并返回非零退出码；错误指出缺少用户名配置，但不输出密码、数据库密码或加密主密钥。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-CFG-002 缺少管理员密码时拒绝启动

- **前置条件**：已配置数据库和加密主密钥；已设置 `SUBPOOL_ADMIN_USERNAME`，未设置 `SUBPOOL_ADMIN_PASSWORD`。
- **步骤**：启动 Subpool 容器；读取退出码和启动日志。
- **期望结果**：服务启动失败并返回非零退出码；错误指出缺少密码配置，但不输出任何敏感值。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-CFG-003 修改管理员环境变量后重启生效

- **前置条件**：服务以一组旧用户名和密码运行，且旧凭据可登录。
- **步骤**：修改用户名和密码环境变量；重启 Subpool 容器；分别用新旧凭据登录。
- **期望结果**：新凭据登录成功；旧凭据登录失败；重启前签发的管理会话全部失效；数据库中不存在管理员密码记录。
- **自动化层级**：`DEPLOY + E2E`
- **优先级**：`P0`

### TC-CFG-004 任意合法公开地址配置

- **前置条件**：准备域名地址、内网地址各一组测试配置，例如 `https://subpool.example.test` 和 `http://subpool.internal.test:8080`。
- **步骤**：分别设置 `SUBPOOL_PUBLIC_URL` 并启动服务；发起设备码授权；查看控制台生成的接入示例。
- **期望结果**：服务不校验或绑定 Gesta 固定域名；接入示例以当前 `SUBPOOL_PUBLIC_URL` 为基准；设备码授权不依赖回调地址或额外端口；地址拼接不存在重复斜杠或路径丢失。
- **自动化层级**：`IT + DEPLOY`
- **优先级**：`P0`

### TC-CFG-005 Secret 注入且镜像不包含真实凭据

- **前置条件**：通过 Compose 环境变量或容器 Secret 注入管理员密码、数据库密码和凭据加密主密钥。
- **步骤**：构建镜像；检查镜像 history、镜像文件系统、容器日志和 `/metrics`。
- **期望结果**：敏感值只在运行时可用，不存在于镜像层、静态资源、日志和指标标签中；`.env.example` 仅含占位值。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

## 5. 管理员登录与会话

### TC-AUTH-001 正确凭据登录

- **前置条件**：服务已启动，管理员环境变量有效。
- **步骤**：向 `POST /api/v1/auth/login` 提交正确用户名和密码；随后访问受保护控制面接口。
- **期望结果**：登录成功；响应设置随机会话 ID Cookie；受保护接口返回成功；响应体不返回管理员密码。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-AUTH-002 错误凭据登录失败并限速

- **前置条件**：服务已启动。
- **步骤**：使用错误用户名、错误密码和空字段分别登录；从同一用户名和来源 IP 连续失败至阈值；再从另一来源执行验证。
- **期望结果**：错误凭据统一返回非泄露性错误；连续失败触发内存限速；同一来源 IP 即使轮换用户名也不能绕过限制；用户名与来源 IP 的组合分别隔离；日志不包含提交的密码。
- **自动化层级**：`UT + IT`
- **优先级**：`P0`

### TC-AUTH-003 管理会话 Cookie 安全属性

- **前置条件**：通过 HTTPS 反向代理访问服务。
- **步骤**：成功登录并检查 `Set-Cookie`；从前端脚本尝试读取 Cookie；执行跨站请求。
- **期望结果**：Cookie 至少包含 `HttpOnly`、`Secure`、`SameSite` 和合理过期属性；浏览器脚本无法读取会话 ID；不安全来源无法直接复用管理会话。
- **自动化层级**：`E2E`
- **优先级**：`P0`

### TC-AUTH-004 注销立即撤销会话

- **前置条件**：管理员已登录。
- **步骤**：访问受保护接口；调用 `POST /api/v1/auth/logout`；再次使用原 Cookie 访问受保护接口。
- **期望结果**：注销成功并清除 Cookie；原会话立即失效；后续访问返回 `401`。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-AUTH-005 服务重启撤销所有管理会话

- **前置条件**：管理员已登录并保存会话 Cookie。
- **步骤**：重启 Subpool 容器但保留 PostgreSQL；使用旧 Cookie 访问控制面。
- **期望结果**：旧会话返回 `401`；数据库中没有可恢复的管理会话；重新登录后正常使用。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-AUTH-006 未认证访问控制面

- **前置条件**：服务已启动。
- **步骤**：不带 Cookie 访问账号、Pool、API Key、usage 等控制面接口；使用数据面 API Key 访问控制面。
- **期望结果**：均返回 `401` 或 `403`；数据面 Key 不能获得管理员权限；响应不泄露资源是否存在。
- **自动化层级**：`IT`
- **优先级**：`P0`

### TC-AUTH-007 不提供在线修改管理员密码接口

- **前置条件**：管理员已登录。
- **步骤**：枚举已注册控制面路由；尝试调用常见的密码修改路径。
- **期望结果**：不存在在线修改管理员用户名或密码的业务接口；凭据只能通过修改环境变量并重启生效。
- **自动化层级**：`IT`
- **优先级**：`P1`

## 6. Codex 设备码授权账号

### TC-DEVICE-001 发起设备码授权

- **前置条件**：管理员已登录，Codex app-server 可启动。
- **步骤**：调用 `POST /api/v1/provider-accounts/codex/device-login`，提交账号显示名称。
- **期望结果**：返回不可猜测的 `login_id`、一次性 `user_code`、HTTPS `verification_url` 和 `expires_at`；不返回 token；不依赖 localhost 回调或额外监听端口。
- **自动化层级**：`IT + CT`
- **优先级**：`P0`

### TC-DEVICE-002 轮询成功并创建账号

- **前置条件**：已发起设备码授权；Mock Server 完成授权并写入有效凭据。
- **步骤**：轮询 `GET /api/v1/provider-accounts/codex/device-login/{id}`；查询账号列表。
- **期望结果**：状态从 `pending` 变为 `completed`；仅创建一个 `provider=codex`、`credential_type=subscription_oauth` 的账号；状态为 `active`；控制台不返回原始 access/refresh token。
- **自动化层级**：`IT + CT`
- **优先级**：`P0`

### TC-DEVICE-002A 连接账号不单独配置容量

- **前置条件**：管理员已登录并打开连接账号对话框。
- **步骤**：检查表单并提交设备码授权请求；检查请求体和创建后的账号记录。
- **期望结果**：表单和请求体仅包含账号显示名称，不出现账号级并发字段；每个账号的请求并发上限由全局 `max_concurrent_requests_per_account` 决定，员工 Key 数量不受此配置限制。
- **自动化层级**：`UT + E2E`
- **优先级**：`P0`

### TC-DEVICE-003 设备码过期和取消

- **前置条件**：准备过期授权、主动取消授权和未知 `login_id`。
- **步骤**：调用状态接口和 `DELETE /api/v1/provider-accounts/codex/device-login/{id}`；在取消边界同步触发成功结果。
- **期望结果**：过期授权返回失败并自动清理；取消后不创建账号；未知或已清理 ID 返回 `404`；授权码和 token 不进入日志。
- **自动化层级**：`UT + IT`
- **优先级**：`P0`

### TC-DEVICE-003A 轮询临时失败后恢复

- **前置条件**：设备授权仍有效；状态接口第一次返回网络错误，随后恢复并返回成功。
- **步骤**：保持授权对话框打开并等待自动重试。
- **期望结果**：前端保留 `login_id` 和一次性代码，采用有界退避继续轮询；恢复后正常完成，不产生孤立授权。
- **自动化层级**：`UT + E2E`
- **优先级**：`P0`

### TC-DEVICE-004 设备码凭据加密存储

- **前置条件**：设备码授权导入成功。
- **步骤**：直接检查数据库中的账号记录；使用正确和错误主密钥尝试解密；查询控制面接口。
- **期望结果**：数据库仅保存 AES-GCM 密文、版本和必要元数据；正确主密钥可解密，错误主密钥失败；接口和日志不暴露明文凭据。
- **自动化层级**：`UT + IT`
- **优先级**：`P0`

### TC-DEVICE-005 手动刷新账号凭据

- **前置条件**：账号存在且 refresh token 有效。
- **步骤**：调用 `POST /api/v1/provider-accounts/{id}/refresh`；随后通过该账号发起请求。
- **期望结果**：刷新成功；新凭据加密覆盖旧版本；账号保持或恢复 `active`；后续请求使用新 access token。
- **自动化层级**：`IT + CT`
- **优先级**：`P0`

### TC-DEVICE-006 同账号并发刷新互斥

- **前置条件**：账号 token 已过期；Mock Server 可统计 refresh 调用次数。
- **步骤**：并发发起多次需要刷新该账号的请求。
- **期望结果**：同一账号同一时刻仅执行一次实际 refresh；等待者复用刷新结果；数据库凭据版本不回退。
- **自动化层级**：`IT`
- **优先级**：`P0`

### TC-DEVICE-007 凭据刷新失败更新账号状态

- **前置条件**：Mock Server 对 refresh 返回不可恢复的认证错误。
- **步骤**：手动或自动触发刷新；查询账号状态；发起新会话请求。
- **期望结果**：账号标记为 `auth_failed`，记录失败时间但不记录 token；调度不再把新 Key 或新会话分配到该账号。
- **自动化层级**：`IT + CT`
- **优先级**：`P0`

## 7. Pool 管理

### TC-POOL-001 创建 Codex Pool

- **前置条件**：管理员已登录，至少存在两个有效 Codex 账号。
- **步骤**：调用 `POST /api/v1/pools` 创建 Pool，设置名称并通过 `provider_account_ids` 同时选择两个账号。
- **期望结果**：Pool 与两个账号成员在同一事务中创建并持久化；内置采用最少绑定优先；模型不做白名单限制；重启后配置仍存在。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-POOL-002 添加账号并更新 Pool

- **前置条件**：Pool 和多个 Codex 账号已存在。
- **步骤**：从管理界面一次选择多个账号加入 Pool；修改 Pool 名称；再通过账号成员接口修改权重、优先级和启用状态。
- **期望结果**：多个成员和策略正确持久化；禁用成员不参与新分配；Pool 不要求配置模型。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-POOL-003 Codex 与付费 API 组成混合 Pool

- **前置条件**：存在仅包含 Codex 订阅账号的 Pool，以及一个健康的 OpenAI-compatible API 账号。
- **步骤**：把 API 账号加入现有 Pool，重新读取 Pool 并创建员工 Key。
- **期望结果**：Pool 自动标记为 `mixed`；订阅账号默认优先级为 `0`，API 账号默认优先级为 `100`；新 Key 优先绑定订阅账号，付费 API 仅作为兜底。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-POOL-004 聚合返回 Pool 可用模型

- **前置条件**：混合 Pool 中多个健康账号分别报告不同且部分重复的模型；API Key 已绑定该 Pool。
- **步骤**：携带该 Key 调用 `/v1/models`，随后重复调用验证短时缓存。
- **期望结果**：返回所有可路由账号模型的去重并集，格式兼容 OpenAI Models API；单个账号发现失败时仍返回其他账号结果；全部失败时返回明确的 Provider 错误。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-POOL-005 Pool 无可用成员错误

- **前置条件**：API Key 对应 Pool 的所有成员均被禁用或处于不可用状态。
- **步骤**：使用该 Key 发起 Responses 请求。
- **期望结果**：返回稳定、可识别的 `subpool_no_eligible_account`；不访问上游；不自动跨 Pool 借用账号。
- **自动化层级**：`IT`
- **优先级**：`P0`

## 8. API Key 生命周期

### TC-KEY-001 生成 OpenAI 风格不透明 Key

- **前置条件**：管理员已登录；Pool 有可用账号槽位。
- **步骤**：多次调用 `POST /api/v1/api-keys`。
- **期望结果**：每个 Key 以 `sk-` 开头，后续为至少 32 字节密码学安全随机数的 Base64URL 表示；Key 唯一、无点号分段、不可从内容解析员工或 Pool 信息。
- **自动化层级**：`UT + IT`
- **优先级**：`P0`

### TC-KEY-002 完整 Key 只展示一次

- **前置条件**：管理员已登录；Pool 有可用账号槽位。
- **步骤**：创建 Key 并保存首次响应；刷新页面、查询相关资源、重启服务后再次查看。
- **期望结果**：完整 Key 只出现在创建成功的首次响应；后续只显示末 4 位提示；数据库仅有 HMAC-SHA256 和提示，不含完整 Key 或可逆密文。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-KEY-003 Key 元数据和策略归属

- **前置条件**：存在 Pool 和健康账号。
- **步骤**：创建带员工名称、scope、速率限制和有效期的 Key；使用 Key 请求允许和不允许的资源。
- **期望结果**：元数据正确保存；Key 只能访问绑定 Pool 和允许模型；客户端传入 Pool ID 或账号 ID 不能改变服务端归属。
- **自动化层级**：`IT`
- **优先级**：`P0`

### TC-KEY-004 撤销 Key 并释放账号槽位

- **前置条件**：Key 已绑定账号且可正常调用。
- **步骤**：调用 `POST /api/v1/api-keys/{id}/revoke`；持续用原 Key 请求；创建新 Key。
- **期望结果**：撤销不可逆；原 Key 最迟 5 秒内失效并返回 `401`；绑定槽位释放；新 Key 可占用释放的槽位；历史日聚合仍可查询。
- **自动化层级**：`IT + E2E`
- **优先级**：`P0`

### TC-KEY-005 无效、过期和错误格式 Key

- **前置条件**：准备随机 Key、篡改 Key、过期 Key 和空 Bearer token。
- **步骤**：分别访问所有数据面端点。
- **期望结果**：统一返回 OpenAI 兼容 `401`；不泄露 Key 是否曾存在、绑定账号或 Pool；不访问上游；不创建 usage。
- **自动化层级**：`IT`
- **优先级**：`P0`

### TC-KEY-006 API Key HMAC 查询防篡改

- **前置条件**：创建一个有效 Key。
- **步骤**：用原 Key 鉴权；修改任意一个字符后再次鉴权；检查鉴权缓存失效行为。
- **期望结果**：只有完整原 Key 的 HMAC 匹配；篡改 Key 被拒绝；缓存中不保存或输出完整 Key；撤销后缓存及时失效。
- **自动化层级**：`UT + IT`

- **期望结果**：前端只能看到显示名、状态、额度和容量元数据；不存在原始 token、密文、主密钥或可用于调用上游的内容。
- **自动化层级**：`E2E + DEPLOY`
- **优先级**：`P0`

### TC-SEC-003 控制面修改审计不记录业务内容

- **前置条件**：管理员已登录。
- **步骤**：创建/更新 Pool、导入/刷新/禁用账号、创建/撤销 Key。
- **期望结果**：每次修改记录 actor、target、动作、结果和时间；不记录管理员密码、完整 API Key、上游凭据、Prompt 或响应正文。
- **自动化层级**：`IT`
- **优先级**：`P1`

### TC-SEC-004 数据面请求不能指定上游账号

- **前置条件**：Key 已绑定账号 A，Pool 中另有账号 B。
- **步骤**：在 Header、查询参数和 JSON 中伪造 Pool ID、账号 ID 和 Provider 字段。
- **期望结果**：服务忽略或拒绝这些越权字段；请求仍按服务端 Key 关系路由；不能跨 Pool、跨账号或跨 Provider。
- **自动化层级**：`IT`
- **优先级**：`P0`

### TC-SEC-005 HMAC 和加密主密钥轮换边界

- **前置条件**：已有 API Key、订阅凭据密文和相应主密钥配置。
- **步骤**：使用错误密钥启动副本或恢复备份；尝试认证 Key 和解密订阅凭据。
- **期望结果**：错误密钥不能误认证或产生乱码凭据；服务明确失败或账号不可用，不把密钥或密文写入日志；不会静默重置数据。
- **自动化层级**：`DEPLOY`
- **优先级**：`P1`

## 16. Docker Compose 自托管

### TC-DPL-001 全新 Docker Compose 启动

- **前置条件**：只有仓库提供的 `Dockerfile`、`compose.yaml`、`.env.example` 和空 Docker 环境。
- **步骤**：填写必要环境变量；构建或拉取镜像；执行 `docker compose up -d`。
- **期望结果**：只启动 Subpool 和 PostgreSQL 两类服务；迁移自动完成；`/healthz` 成功，依赖就绪后 `/readyz` 成功；控制台静态资源由 Go 服务提供。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-DPL-002 PostgreSQL 数据卷持久化

- **前置条件**：已创建账号、Pool、API Key 绑定和 usage。
- **步骤**：停止并删除容器但保留命名卷；重新执行 `docker compose up -d`。
- **期望结果**：持久数据完整恢复；API Key 继续有效；管理会话因进程重启失效；无需重新执行设备码导入。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-DPL-003 自定义域名、内网域名和反向代理

- **前置条件**：准备测试 TLS 反向代理和多个合法 Host；DNS 由部署者自行管理。
- **步骤**：用自定义公网域名和内网域名分别代理同一 Subpool；执行登录、设备码授权和数据面请求。
- **期望结果**：功能不依赖 `*.gesta.run` 或任何共享域名；配置的域名均可使用；设备码授权不依赖当前域名；Subpool 不尝试修改 DNS。
- **自动化层级**：`DEPLOY + E2E`
- **优先级**：`P0`

### TC-DPL-004 健康与就绪探针

- **前置条件**：Compose 已运行。
- **步骤**：正常访问探针；暂停 PostgreSQL；恢复 PostgreSQL；模拟上游不可用。
- **期望结果**：进程存活时 `/healthz` 反映服务存活；关键依赖不可用时 `/readyz` 失败；依赖恢复后自动转为就绪；上游故障不会错误报告数据库健康。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-DPL-005 单实例约束

- **前置条件**：Compose 默认配置可检查。
- **步骤**：检查服务副本数、依赖和运行配置；尝试使用文档默认命令启动。
- **期望结果**：默认只运行一个 Subpool 实例；不依赖 Redis、Kafka、Helm 或 Kubernetes Operator；进程内会话和限流的单实例限制在部署文档中明确说明。
- **自动化层级**：`DEPLOY`
- **优先级**：`P1`

## 17. 故障、升级、备份与恢复

### TC-REC-001 PostgreSQL 启动晚于 Subpool

- **前置条件**：清空环境；让 PostgreSQL 延迟就绪。
- **步骤**：同时启动 Compose 服务。
- **期望结果**：Subpool 不在未迁移状态接受流量；通过健康检查或有界重试等待 PostgreSQL；数据库就绪后自动迁移并转为 ready，或明确退出由 Compose 重启。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-REC-002 请求期间 PostgreSQL 暂时不可用

- **前置条件**：服务正常且存在有效 Key；准备中断 PostgreSQL。
- **步骤**：中断数据库连接；发起需要鉴权、绑定或 usage 写入的请求；恢复数据库。
- **期望结果**：不能安全验证或调度时快速返回可识别错误，不绕过鉴权或超配；连接池不会永久卡死；恢复后服务自动重新就绪并继续处理请求。
- **自动化层级**：`DEPLOY + IT`
- **优先级**：`P0`

### TC-REC-003 Subpool 进程崩溃后恢复

- **前置条件**：已有持久配置、Key、绑定和 usage；存在已登录管理会话。
- **步骤**：强制终止 Subpool 容器；由 Compose 重启；再次调用管理面和数据面。
- **期望结果**：旧管理会话失效；持久 API Key、绑定、账号和 usage 保留；短暂不可用后数据面恢复；不重复累计崩溃前已确认的 usage。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-REC-004 PostgreSQL 备份与恢复

- **前置条件**：数据库包含账号密文、Pool、Key、绑定和 usage；保存当前加密/HMAC 主密钥。
- **步骤**：按官方文档备份；删除原容器和数据卷；创建新卷并恢复；以相同密钥启动。
- **期望结果**：所有持久对象和聚合值完整恢复；已有 Key 可鉴权；订阅凭据密文可解密；完整 API Key 和聊天内容不出现在备份中。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-REC-005 正向版本升级和自动迁移

- **前置条件**：运行上一受支持版本并准备代表性数据；新版本包含数据库迁移。
- **步骤**：备份；拉取新镜像；执行 `docker compose up -d`；验证迁移和核心链路。
- **期望结果**：迁移只执行一次且成功；旧数据兼容；账号、Pool、Key、绑定和 usage 保留；登录、Responses、SSE 和撤销 Key 正常；升级步骤无需额外安装脚本。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-REC-006 迁移失败时安全停止

- **前置条件**：构造会失败的迁移环境或只读数据库。
- **步骤**：启动新版本容器。
- **期望结果**：Subpool 不进入 ready，不在部分迁移状态承接请求；返回非零退出或保持不就绪；日志指出迁移阶段但不泄露敏感数据；原备份可用于恢复。
- **自动化层级**：`DEPLOY`
- **优先级**：`P0`

### TC-REC-007 备份恢复到任意自托管域名

- **前置条件**：从域名 A 的实例取得数据库备份和所需 Secret；准备域名 B 的全新 Compose 环境。
- **步骤**：在域名 B 恢复数据库；更新 `SUBPOOL_PUBLIC_URL`；启动并重新登录；验证 API Key 和新设备码授权。
- **期望结果**：持久业务数据不绑定旧域名；已有 API Key 继续有效；接入示例使用域名 B；设备码授权不依赖旧域名或本地回调；旧管理会话不恢复。
- **自动化层级**：`DEPLOY + E2E`
- **优先级**：`P1`

### TC-REC-008 上游协议变化时快速禁用账号

- **前置条件**：Mock Server 返回未知或不兼容协议响应；账号位于活动 Pool。
- **步骤**：触发契约失败；通过管理端禁用账号；继续发起新请求。
- **期望结果**：异常响应不会导致进程崩溃或泄露凭据；禁用操作快速生效；新 Key 和新会话不选择该账号；其他账号继续服务。
- **自动化层级**：`CT + IT`
- **优先级**：`P0`

## 18. 发布验收最小集合

每次合并前至少执行以下自动化门禁：

1. 全部 `UT`。
2. PostgreSQL + Codex Mock Server 的全部 `P0 IT/CT`。
3. Responses、Chat Completions、Models、SSE、设备码授权、Key 撤销的 `P0 E2E`。
4. Docker Compose 全新启动、持久卷重启、备份恢复、正向升级和迁移失败测试。
5. 日志/数据库敏感哨兵扫描与“不保存聊天内容”测试。

真实 Codex 设备码授权冒烟测试仅在受控发布环境执行，使用专用测试账号，不进入普通 CI；结果不得包含真实 token 或聊天内容。

## 19. 已冻结契约与待完善项

Phase 1 已冻结以下测试契约：Codex 使用设备码授权且不依赖回调端口；重复导入同一 Codex 账号返回失败状态；API Key 的作用域为 `responses`、`chat_completions`、`models` 或 `*`；速率限制按单 Key 每分钟请求数计算；日期聚合使用 UTC；429 优先采用 `Retry-After`，缺失或无效时默认冷却一分钟；新会话切换账号时同步迁移 API Key 的持久绑定；usage 写入失败不篡改已经返回给客户端的推理结果。

以下项目需要在后续版本继续完善测试或运维契约：

1. Phase 1 的 `SUBPOOL_PUBLIC_URL` 只接受不带路径、查询、片段或内嵌凭据的 origin；路径前缀支持留待后续版本。可信代理通过 `SUBPOOL_TRUSTED_PROXY_CIDRS` 显式配置，未受信来源的 `X-Forwarded-For` 会被忽略。
2. API Key HMAC 主密钥的在线轮换流程；当前只支持部署时通过 `SUBPOOL_API_KEY_HMAC_KEY` 注入。
3. 真实 Codex 上游变化后的 Responses、Chat Completions、SSE 和工具调用契约样例维护。
4. 数据库跨版本升级跨度、失败回滚策略和历史 usage 保留阈值。
5. p95 首包开销、慢客户端背压、长期运行资源占用和大规模 Key 数量下的容量基准。
6. `usage_event_dedup` 的保留期和自动清理任务；Phase 1 先保证精确计量，表中只保存不可逆事件哈希。
